# patterns — 型態訊號

## Purpose

在清單上標示「這檔現股今天走出了哪個型態」,並讓使用者用型態 chip 篩選標的。

架構決定:**沿用來源端算好的訊號,不在前端自算幾何**。理由是同一套型態若前端
自算、行動 App 另算,兩邊必然漂移;使用者會看到同一檔在兩處狀態不同。因此本站
只讀「這檔今天有沒有命中」,幾何定義的正本留在來源端。

## Requirements

### R1: 六個型態槽位與來源
型態在本系統是**可配置的六個槽位**,不是寫死的名單。每個槽位接一個來源:

| 槽位 | 設定鍵(`tables.py`) | 來源型式 |
|---|---|---|
| 型態A | `pattern_a` | 資料集表 或 訊號頻道 |
| 型態B | `pattern_b` | 同上 |
| 型態C | `pattern_c` | 同上 |
| 型態D | `pattern_d` | 同上 |
| 型態E | `pattern_e` | 同上 |
| 型態F | `pattern_f` | 同上 |

兩種來源型式的差異(`refresh.py` 各有一個分支):
- **資料集表**:每日更新的批次表,一列一檔命中標的。日 K 級。
- **訊號頻道**:事件型端點(`PROVIDER_SIGNAL_URL`),回 `[標的代號, 訊號時間 ms, 是否成立]`。
  每輪 refresh 取當下快照。**注意兩者不可混用**:把頻道 id 當表 id 去打,
  多數平台會回 0 欄而不是報錯 —— 這正是 R3 要抓的情況。

前端的型態名在 `web/src/logic.js` 的 `PICK_CHIPS` 定義(`id` 與 `label` 同字串,
`patternQualify(name)` 直接比對 `r.pattern`)。改成你的型態真名時,
前後端兩邊的字串要一致。

### R2: 一檔一型態,先到先得
每檔現股只掛**一個**型態 tag。批次表先跑,訊號頻道後跑、只補還沒被佔到的標的
(`pmap.setdefault`)。若你的型態有優先順序(例如課綱型態優先於衍生型態),
就靠這個先後順序表達。

### R3: 不得靜默(patternIssues 台帳)
型態是輔助訊號,壞掉不該讓整站掛掉——但也絕不能默默消失。

#### Scenario: 來源回 0 欄
- WHEN 某型態來源回 0 欄
- THEN 記入 `meta.patternIssues`(語意:「來源壞了或 id 失效」,**不是**今天沒命中)
- AND 站台照常出其他資料

#### Scenario: 來源有欄位但 0 列
- WHEN 來源有欄位、0 列
- THEN 視為「今天沒有標的命中」,正常不吵

#### Scenario: 取數拋例外
- WHEN 打表/頻道拋例外
- THEN 記 patternIssues(含型態與 id),不讓整輪 refresh 失敗

`/api/meta` 另回 `pattern_stats`(每型態的 cols/rows),用來事後對照
「是來源空了,還是我們讀錯欄位」。

## 原型狀態

型態命名(型態A~F)是**佔位**,六個槽位的來源 id 全空;demo 資料把型態隨機指派給
部分標的,並確保這些標的同時滿足精選門檻,讓旗艦頁有內容。
接真來源與移除方式見 [PROTOTYPE_TRUTH.md](../../../PROTOTYPE_TRUTH.md) #3。

## Out of scope
- 在本系統自算型態幾何、回測、歷史型態訊號序列
- 型態在不同時間框(日/時/即時)的變體差異——由來源端定義
